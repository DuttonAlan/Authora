# ISS-004 – `ModifiedAt` is not updated when only a collection of an entity changes

- **Status:** Resolved (2026-10-11)
- **Found:** 2026-10-11, in the code review of `feature/add-identity-endpoints`
- **Area:** Persistence (`ModifiedAtInterceptor`)

## Problem

`ModifiedAtInterceptor` only set `ModifiedAt` on entities whose own row was modified. Many changes do not touch the row of the entity itself, but only its children or its many-to-many links:

| Change | Rows that change | Entity that should get a new `ModifiedAt` |
|---|---|---|
| Assign or remove a Role | `user_roles` | User |
| Grant or revoke a Permission | `role_permissions` | Role |
| Add or remove a Redirect URI | `client_redirect_uris` | Client |
| Allow or disallow a Scope | `client_scopes` | Client |
| Create or revoke a Secret | `client_secrets` | Client |

For all of these, `GET` showed an outdated `ModifiedAt`, although the resource had changed.

## Impact

- `ModifiedAt` could not be trusted to tell when a User, Role or Client was last changed. Security-relevant changes, such as a new administrator Role or a new Client Secret, were not visible in it.

## Cause

The interceptor only looked at `EntityState.Modified` of the entity itself. EF Core tracks the rows above as separate entries (`Added`, `Deleted` or `Modified`), so the entity they belong to stayed `Unchanged`.

## Fix

The interceptor also sets `ModifiedAt` on the entity that a changed row belongs to. A row belongs to an entity if the entity navigates to it as a collection:

- through a collection navigation, e.g. `Client.Secrets` and the owned `Client.RedirectUris`, or
- through a many-to-many skip navigation, e.g. `User.Roles` via `user_roles`.

Only the side with the navigation is changed. Assigning a Role changes the User, but not the Role; allowing a Scope changes the Client, but not the Scope.

During testing, a second problem showed up: for many-to-many relationships that are only navigable from one side, EF Core still creates a skip navigation for the other side (e.g. from Role back to its Users), but without a CLR member. Without handling this, assigning a Role also changed the `ModifiedAt` of the Role, and granting a Permission changed the Permission. The interceptor ignores these shadow navigations.

Other cases:

- A deleted row uses its original foreign key value to find the entity it belonged to.
- Entities that are created or deleted in the same save are not changed, so new entities still start with `ModifiedAt = null`.
- Requests that change nothing (e.g. removing a Role that is not assigned) do not change `ModifiedAt`.

## Verification

Tested manually against a fresh database by reading `modifiedAt` before and after each request:

| Request | `modifiedAt` of the entity | `modifiedAt` of the other side |
|---|---|---|
| Assign and remove a Role | User changed | Role unchanged |
| Grant and revoke a Permission | Role changed | Permission unchanged (still `null` in the database) |
| Add and remove a Redirect URI | Client changed | – |
| Allow and disallow a Scope | Client changed | Scope unchanged |
| Create and revoke a Secret | Client changed | – |
| Update the Name of a Client | Client changed (unchanged behaviour) | – |
| Remove a Role that is not assigned, revoke a revoked Secret | Unchanged | – |
| Register a Client with a Secret and a Redirect URI | `null` | – |
| Delete a Client with Secrets | 204, no errors | – |

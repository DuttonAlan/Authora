# ISS-001 – Every `InvalidOperationException` is returned as 409 Conflict with its message

- **Status:** Resolved (2026-10-11)
- **Found:** 2026-10-11, in the code review of `feature/add-identity-endpoints`
- **Area:** Error handling (`ProblemDetailsExceptionHandler`)

## Problem

`ProblemDetailsExceptionHandler` mapped every `InvalidOperationException` to `409 Conflict` and returned its `Message` as the `detail` of the response.

It was meant for three rules in the domain that throw `InvalidOperationException`:

- A System Role cannot be renamed (`Role.SetName`).
- The administrator Role cannot lose Permissions (`Role.RevokePermission`).
- A Public Client cannot have Secrets (`Client.AddSecret`).

But `InvalidOperationException` is also thrown by framework code for bugs, e.g. by EF Core (`The instance of entity type ... cannot be tracked`), by LINQ (`Sequence contains no elements`) or by dependency injection.

## Impact

- Bugs were reported as `409 Conflict`, which tells the client that its request conflicts with the current state. The client could not tell a bug from a rule violation, and the bug was not visible as a server error.
- Internal details, such as entity and service names, were sent to the client in `detail`.

## Cause

The mapping in [identity-access-plan.md](../identity-access-plan.md) listed `InvalidOperationException` → 409 next to `ConflictException`, so the domain rules did not need their own exception type. The handler cannot tell a domain rule from a framework error, because both use the same exception type.

## Fix

- The handler only maps `ConflictException` to 409. `InvalidOperationException` is no longer mapped and results in `500 Internal Server Error` without the message, like every other unexpected exception.
- The services check the three rules before calling the domain and throw `ConflictException`:
  - `UpdateRoleService`: renaming a System Role.
  - `RevokePermissionService`: revoking a Permission from the administrator Role.
  - `CreateClientSecretService`: creating a Secret for a Public Client.
- The domain still throws `InvalidOperationException` for these rules as a safety net. If it is ever reached, a service is missing the check, which is a bug and correctly results in 500.

## Verification

Tested manually against a fresh database:

| Request | Result |
|---|---|
| Rename the System Role `admin` | 409, `The Name of a System Role cannot be changed.` |
| Update the `admin` Role with its current Name and a new Display Name | 204 |
| Revoke a Permission from the `admin` Role | 409, `Permissions cannot be revoked from the administrator Role.` |
| Create a Secret for a Public Client | 409, `Only Confidential Clients can have Secrets.` |

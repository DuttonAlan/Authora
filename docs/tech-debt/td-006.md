# TD-006 – Removing Roles or Permissions does not invalidate existing Sessions and tokens

- **Status:** Open
- **Added:** 2026-10-11
- **Area:** Users and Roles (`RemoveRoleService`, `DeleteRoleService`, `RevokePermissionService`)

## Current state

These operations reduce the effective Permissions of Users, but do not rotate their `SecurityStamp`:

- Removing a Role from a User (`DELETE /api/users/{id}/roles/{roleId}`).
- Deleting a Role (`DELETE /api/roles/{id}`), which removes it from all Users through the cascade on `user_roles`.
- Revoking a Permission from a Role (`DELETE /api/roles/{id}/permissions/{permissionId}`), which affects all Users with this Role.

Deactivating, deleting and revoking the sessions of a User do rotate the `SecurityStamp`.

## Why

Sessions and tokens do not exist yet. Whether a change of Permissions must invalidate them depends on how the access checks are designed (US-032): if the Permissions are read for every request, nothing needs to be invalidated; if they are stored in tokens or Sessions, the old values stay valid until these expire.

## Impact

- Today: none, because no tokens or Sessions are issued yet.
- Once they exist and contain Permissions: a User keeps Permissions that were removed until the token or Session expires, e.g. an administrator whose administrator Role was removed.

## How to resolve

When designing the access checks (US-032):

1. Decide whether Permissions are read for every request or stored in tokens and Sessions.
2. If they are stored, rotate the `SecurityStamp` of every affected User, in the same transaction as the change:
   - `RemoveRoleService`: the User.
   - `DeleteRoleService` and `RevokePermissionService`: all Users with the Role, with a single bulk update instead of loading each User.
3. Access Tokens that are checked without calling Authora stay valid until they expire (`AccessTokenTTL`). A short `AccessTokenTTL` limits this window, as described in [TD-002](td-002.md).

Granting Roles or Permissions does not need this, as it only adds access.

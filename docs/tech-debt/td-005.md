# TD-005 – The Email of a deleted User can never be used again

- **Status:** Open
- **Added:** 2026-10-11
- **Area:** Users (`DeleteUserService`, `UserRepository.EmailExists`, `UserConfiguration`)

## Current state

- Deleting a User is a soft delete: the User is set to `UserState.Deleted` and keeps its `Email` and `NormalizedEmail`.
- The unique index on `users.NormalizedEmail` and `UserRepository.EmailExists` include deleted Users.
- As a result, creating a User with the Email of a deleted User, or changing an Email to it, returns `409 The Email is already used by another User.`

## Why

The soft delete keeps the record for history, as planned in [identity-access-plan.md](../identity-access-plan.md). Whether a deleted Email may be used again is a product decision that has not been made yet. It also depends on data protection requirements.

## Impact

- A person whose account was deleted cannot get a new account with the same Email.
- The error message is confusing, because the deleted User is not shown in `GET /api/users` unless filtered by `state=Deleted`.
- Keeping the Email of a deleted User may conflict with the right to erasure (GDPR, Article 17), depending on how long the history must be kept.

## How to resolve

Decide on one of these approaches:

1. **Allow reuse:** replace the unique index with a filtered one (`HasFilter("\"State\" <> 3")`), create the migration with `dotnet ef migrations add`, and exclude deleted Users in `EmailExists`. Every lookup by Email (e.g. sign-in) must then also exclude deleted Users.
2. **Anonymize on delete:** when a User is deleted, replace the Email with a unique placeholder, e.g. `deleted-<id>@invalid`, and clear the Name. This frees the Email and removes personal data, while the record and its Id stay for history.
3. **Keep it blocked:** keep the current behaviour by design and only change the error message, e.g. `The Email belongs to a deleted User.`

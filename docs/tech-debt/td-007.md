# TD-007 – Browser-based Clients cannot call the token endpoint (no CORS)

- **Status:** Open
- **Added:** 2026-10-11
- **Area:** OAuth (`OAuthController`: `/oauth/token`, `/oauth/revoke`)

## Current state

Authora does not send CORS headers. A single-page app on another origin can redirect the User to `/oauth/authorize`, but the browser blocks its `fetch` to `/oauth/token` and `/oauth/revoke`.

Server-side Clients, mobile and desktop apps are not affected.

## Why

The allowed origins must come from the registered Clients, e.g. the origins of their Redirect URIs, which needs a policy that reads the database for every preflight request. A static list in the configuration would drift from the registered Clients. This was left out of the first version of the OAuth core.

## Impact

- Public Clients that run in the browser (SPAs) cannot use Authora directly. They need a backend that exchanges the code (the "backend for frontend" pattern), which is the more secure setup anyway.

## How to resolve

1. Add an `ICorsPolicyProvider` for `/oauth/token` and `/oauth/revoke` that allows an `Origin` only if it is the origin of a registered Redirect URI of an enabled Client. Cache the list of origins briefly.
2. Allow only `POST`, the `Content-Type` and `Authorization` headers, and no credentials (cookies).
3. Never enable CORS for `/oauth/authorize`, `/account/*` and `/api/*`.

# TD-003 – The admin API has no authentication or authorization

- **Status:** Open
- **Added:** 2026-10-11
- **Area:** API (`UsersController`, `RolesController`, `PermissionsController`, `ScopesController`, `ClientsController`, `/health`)

## Current state

- All endpoints under `/api/users`, `/api/roles`, `/api/permissions`, `/api/scopes` and `/api/clients` can be called by anyone who can reach Authora. There is no authentication and no permission check.
- They are mapped in every environment, not only in Development.
- `GET /health` also returns the names of the applied, pending and unknown migrations to anyone, which reveals the exact schema version.

## Why

Authentication needs the OAuth runtime (sign-in, Sessions, tokens), which is planned for a later phase. The permission checks (US-032) need these tokens and the `Permissions` constants, which do not exist yet either. See the open decisions in [identity-access-plan.md](../identity-access-plan.md#open-decisions).

## Impact

- Anyone with network access can, for example, give themselves the administrator Role, create a Client Secret, or delete Users.
- Authora must not be run where untrusted clients can reach it until this entry is resolved.

## How to resolve

1. **Until authentication exists**, choose one temporary protection:
   - Map the admin controllers only in Development, or
   - Require an API key, e.g. in an `X-Api-Key` header. Store only its hash in the configuration, compare it in constant time, and fail at startup if it is missing outside Development.
2. **Once tokens exist**, protect every endpoint with `[Authorize(Policy = "<permission>")]`, backed by a permission-based `IAuthorizationHandler` (US-032) that checks the Permissions of the User through its Roles. Add the `Permissions` constants and seed them (step 3 of the plan).
3. **For `/health`**, return only the overall status to anonymous callers, and the details of each check only to authorized callers or internal networks. `/health/live` can stay public.

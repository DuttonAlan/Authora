# Changelog

All notable changes to Authora are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Authora uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, minor versions may contain breaking changes; they are listed under *Changed* or *Removed*.

## [Unreleased]

### Added

- Remembered consent for third-party Clients. Approving a Client on the consent screen is stored as the User's Consent for it, so the User is only asked again when the Client requests a Scope the Consent does not contain; approving that adds the Scope. `prompt=consent` still always shows the screen, and `prompt=none` now gets a code instead of `consent_required` when the Consent covers the request. Users see and withdraw their Consents under *Connected applications* at `/account/consents` (linked from the sign-in page and the consent screen); administrators list and revoke them with `GET /api/users/{id}/consents` (`users.read`) and `DELETE /api/users/{id}/consents/{clientId}` (`users.manage-access`) or in the new **Consents** panel of a User in the admin interface. Revoking a Consent revokes the User's Grants for the Client, so its Access and Refresh Tokens for the User stop working, and codes issued before are rejected, also after the User approves again: each code is bound to the Consent it was issued under (log event 6016). Deleting a Scope removes it from all Consents; deleting a User deletes their Consents. New audit events `consent.granted` and `consent.revoked`, log events 15001–15002, and the tables `auth.consents` and `auth.consent_scopes` and the column `auth.authorization_codes.ConsentId` (need the migrations `RememberedConsent` and `BindAuthorizationCodeToConsent`). First-party Clients are unchanged and store no Consent, also not after `prompt=consent`.
- Self-service password change at `/account/password`: a signed-in User enters the current password and a new one (same policy as the admin API, 12 to 128 characters). The Session of the change stays valid; all other Sessions and all Grants of the User with their Access and Refresh Tokens are revoked. A wrong current password counts towards the lockout, and attempts share the sign-in rate limit. Users get a notification email when email delivery is configured. New audit event `account.password-changed` (also recorded as `Failed` for a wrong current password or a lockout) and log events 5009–5011. The sign-in page and the admin interface (lock icon next to **Sign out**) link to the page.
- Email delivery through SMTP, the building block for password reset and email verification. Settings under `Authora:Email` (host, port, TLS mode `StartTls`/`Implicit`/`None`, credentials, sender, timeout, and a trusted certificate for private CAs); email stays off while `Authora:Email:Host` is not set. Outside `Development` and `Testing`, Authora refuses to start with TLS mode `None`. Emails have a plain-text and an HTML version. One-time tokens for email links are stored only as SHA-256 hashes in the new table `auth.email_tokens` (needs the migration `EmailTokens`), expire after at most a day, work once, only for their purpose and only while the User keeps the address, and are removed by the cleanup. New log events 14001–14006 and 14011–14014. Docker Compose includes the mail catcher Mailpit at <http://localhost:8025>; the [Getting started](docs/tutorials/getting-started.md) tutorial now creates a certificate for it.
- Client Credentials grant for machine-to-machine access: `grant_type=client_credentials` at `/oauth/token` gives a Confidential Client an Access Token for itself, without a User, Refresh Token or ID Token. Opt-in per Client (Grant Type `client_credentials`, never allowed by default and never for Public Clients). Requested Scopes must be allowed for the Client and must not be System Scopes; without `scope`, the token gets all allowed non-system Scopes. Introspection reports the Client as `sub`; UserInfo and the admin API reject these tokens. New audit event `client.token-issued` and log event 6014; `grant_types_supported` lists `client_credentials`.
- RP-initiated logout ([OpenID Connect RP-Initiated Logout 1.0](https://openid.net/specs/openid-connect-rpinitiated-1_0.html)): applications sign Users out of Authora through the `end_session_endpoint` `/oauth/logout`, with `id_token_hint` (also expired), `client_id`, `post_logout_redirect_uri` and `state`. Users confirm on a page unless the hint belongs to their current Session. Post-logout Redirect URIs are registered per Client (`POST`/`DELETE /api/clients/{id}/post-logout-redirect-uris`, `postLogoutRedirectUris` at registration, the admin interface). New audit events `account.signed-out-by-client`, `client.post-logout-redirect-uri-added` and `client.post-logout-redirect-uri-removed`, log events 4019, 4020, 5008 and 6013. The conformance workflow also runs the suite's RP-Initiated Logout OP test plan.
- Website with the documentation at <https://authora.alandutton.de/>, built from `docs/`.
- Admin interface: **Audit log** → **Verify chain** checks the hash chain of the audit log (Permission `audit.verify`) and shows the last link to compare with a checkpoint.
- The OpenID Foundation conformance suite's Basic OP test plan runs against the container on every pull request (`.github/workflows/conformance.yml`, `tests/conformance/`); deviations from the recorded results fail the build. See [Run the conformance tests](docs/how-to/run-the-conformance-tests.md).
- PKCE can be made optional for a single Confidential Client, for OpenID Connect libraries that do not send it: `PUT`/`DELETE /api/clients/{id}/pkce-optional` (Permission `clients.update`), *Make PKCE optional* in the admin interface, `isPkceOptional` in the Client details, audit events `client.pkce-made-optional` and `client.pkce-required`, log events 4017 and 4018. PKCE stays required by default and for Public Clients, and existing Clients keep requiring it. A `code_verifier` for a code requested without `code_challenge` is rejected, so a flow that uses PKCE cannot be downgraded.
- Authorization requests sent with `POST /oauth/authorize` as a form (OpenID Connect Core 1.0, Section 3.1.2.1). They are redirected to the same request as GET, so a signed-in User is recognized. Before, they failed with `400 Bad Request`.

### Changed

- Redesigned admin interface. A grouped sidebar (a drawer on phones) and a breadcrumb; the start page shows failed events of the last 24 hours, recent activity and the size of the directory; the audit log is drawn as the chain it is sealed into, grouped by day, with the rarely used filters folded away; pages of Users, Groups, Roles, Clients and Scopes start with their state and a copyable Id; Permissions of a Role are grouped by area. Destructive and security-relevant actions are confirmed in a dialog with Cancel focused instead of the browser's prompt. Table rows are links, so they can be reached with the keyboard. Follows the system's light or dark appearance and honors reduced motion, reduced transparency and increased contrast.
- Website: the homepage states the project's status next to the call to action and shows how an application signs users in through Authora, and its icons, button contrast, 404 page and link previews are improved.
- The admin interface shows the reason of a `403` from the API when there is one, e.g. which Permissions are missing for a Role assignment.
- Website: redesigned homepage. The sign-in flow is drawn as a sequence diagram between the application and Authora; features are grouped by who uses them (applications, administrators, operators); a section lists the implemented specifications and the conformance test plans that run on every pull request; another states what is not supported and the project's status; the four parts of the documentation are linked at the end.

### Fixed

- Website: the diagram on the admin interface page failed to render and put an error at the bottom of the page. The architecture diagram no longer clips labels or shrinks below a readable text size, and all diagrams have text descriptions.
- **Security:** delegated admin Permissions could be turned into administrator rights. `users.assign-roles` could assign `admin` (also to oneself), `roles.grant-permissions` could extend one's own Role, `groups.manage-members` and `groups.assign-roles` could reach more powerful Roles through a Group, and `users.set-password`, `users.manage-access`, `users.update` and `users.delete` also worked on administrators, e.g. to set an administrator's password and sign in as them. Now nobody grants more than they hold: a caller who is not an administrator can only give out Permissions they hold and only act on Users whose effective Permissions they all hold; only administrators assign `admin` or act on administrators. A violation returns `403 Forbidden` with the reason, is recorded in the audit log as the attempted event with outcome `Failed`, and logged as event 13001. See [Admin API](docs/reference/admin-api.md#nobody-grants-more-than-they-hold). The documentation now marks `clients.manage-first-party` as equivalent to `admin`.
- **Security:** `/oauth/introspect` had no rate limit, so Client Secrets could be guessed there without limit. It now shares the limit of `/oauth/token` and `/oauth/revoke` (`Authora:RateLimiting:TokenPermitsPerMinute`); resource servers that introspect every request may need a cache or a higher limit.
- **Security:** an Authorization Code issued just before the User signed out could still be exchanged until it expired. Codes are now bound to the Session in which they were issued and get `invalid_grant` once it has ended (signed out, expired or idle); log event 6015. Requires the migration `BindAuthorizationCodeToSession`; codes issued before it cannot be exchanged.

## [0.1.0] - 2026-11-02

First public version.

### Added

- OAuth 2.1 authorization server: Authorization Code grant with mandatory PKCE (`S256`), rotating Refresh Tokens with reuse detection, revocation (RFC 7009), introspection (RFC 7662), `iss` in authorization responses (RFC 9207).
- OpenID Connect provider: discovery, ID Tokens (`RS256`), JWKS, UserInfo, Scopes `openid`, `profile` and `email`, `nonce`, `prompt` and `max_age`.
- Signing keys from PEM files, reloaded without a restart for key rotation.
- Password sign-in with Sessions, lockout and rate limits; consent screen for third-party Clients; first-party Clients.
- Users, Groups, Roles and Permissions for administering Authora; Scopes and Clients with Redirect URIs, allowed and served Scopes, and expiring Secrets.
- Admin API and admin interface with a backend for frontend that keeps tokens out of the browser.
- Audit log with a tamper-evident hash chain and verification endpoint.
- Startup checks that refuse insecure production settings; security headers; health checks; cleanup of expired data.
- Container images for the server and the database migrations, and a Docker Compose setup for local evaluation.
- Documentation following Diátaxis: tutorials, how-to guides, reference and explanation.
